# 07. 日常操作と記録・運用ルール

更新日: 2026-09-06

## 1. この資料の状態

今回の設計対話で合意した製品の方向性と、それを具体化する運用案を記録する。
実装済みの仕様や本番への変更指示ではない。

- **Accepted**: 利用者が明示的に選択、または画面案を確認して受け入れた内容。
- **Recommended**: 合意した目的を満たすための詳細案。実装時の契約に落とし込む。
- **Open**: 追加の判断・仕様確認が必要な内容。

[既存設計の入口](README.md)と00〜06の資料は引き続き参照する。
今回の機能優先順位と画面の基本構成は本資料のAcceptedを参照し、技術選定や
未決定事項まで承認済みとは扱わない。保護された挙動と運用境界は変更しない。

ソースには既にv2の基盤と読み取り専用画面などがある。今後の実装計画では
実装済み範囲を再確認して利用し、v2への全面移行が済んでいるとは扱わない。
この設計作業では実データ・認証情報・実行環境の状態を確認していない。

## 2. Accepted: 目的と機能の優先順位

最優先は「配信中の操作・確認を楽にする」。別モニターで常時表示して使う。

| 領域 | 合意した扱い |
|---|---|
| 配信履歴 | 平均同接・最大同接・推移を中心にする。配信中のイベントも記録する |
| 配信比較 | 同じカテゴリーの前回配信を初期候補とし、任意の配信にも切り替えられる |
| 配信セット | タイトル・カテゴリー・タグの作成、編集、保存、差分確認、適用を主要操作にする |
| 視聴者リスト | ライブ画面に常設し、メモと参加履歴へつなげる |
| フォロワー履歴 | フォロー・解除を確認した履歴・再フォローを追えるようにする |
| 見どころメモ・マーカー | Twitchの配信マーカー作成と、このツール内のメモ・履歴を追加する |
| 自動チャット投稿 | 機能を残す。現在は使わないため初期状態は無効 |
| チャンネルポイント予想 | 機能を残す。現在は使わないため初期状態は無効 |
| チャットコマンド | 将来用として実装対象に含める。初期状態は無効 |

VODと外部配信ステータスAPIは既存の保護範囲として維持する。
今回の主要画面から目立たなくすることと、機能を削除することは区別する。

## 3. Accepted: 主要4画面の基本構成

対話中に提示した画面案は架空データによるプレビューであり、アプリへの実装ではない。
具体的な画面仕様は以下を引き継ぎ、以前の[UI設計](02-information-architecture-and-ui.md)と整合させる。
プレビューに使った個人のローカルパスやサンプル値は実装要件にしない。

### ライブ

- 上部に配信状態、経過時間、接続・記録状態、配信セット、マーカー操作。
- 視聴者リストと今回の同接推移・アクティビティを並べる。
- 新着イベントや定期更新で操作位置・リストの並び順を勝手に動かさない。
- 正常時の表示は静かにし、記録停止・操作失敗など対処が必要な変化を目立たせる。
- 将来用機能は有効にしたものの操作を表示する。

### 配信履歴

- 一覧に日付、タイトル、カテゴリー、平均同接、最大同接、配信時間、新規フォロー数。
- 詳細で同接グラフとイベント・マーカーを同じ時間軸で確認する。
- 比較では配信開始からの経過時間をそろえ、各配信全体の集計と区別する。
- 配信時間、レイド、欠測、カテゴリーの違いを比較時の背景として確認できる。

### コミュニティ

- 視聴者一覧とフォロワー履歴を切り替え、名前から同じ人物詳細を開く。
- 人物詳細に自分用メモ、参加した配信、フォローの履歴を表示する。
- 未確認と未フォロー、参加の記録なしと参加ゼロを区別する。
- 人を切り替えてもメモの下書きを保持する。
- ライブ画面からも同じ人物詳細を開ける構成にする。

### 配信セット

- 保存とTwitchへの適用を別操作にする。保存だけで配信を変更しない。
- 適用前に現在と適用後のタイトル・カテゴリー・タグを比較する。
- 編集中の下書きを保持し、未保存の変更がある間は適用に進めない。
- 変更なしの送信、連打による二重適用を防ぐ。
- 空のタグ一覧はタグを外す指定として明示する。
- 告知用タグはTwitch用タグと区別して保持する。
- プレビューのカテゴリー候補3件や失敗シナリオは例示。実装では検索と
  Twitch側の実際の応答・再確認結果から、成功・失敗・結果不明を判断する。

## 4. Accepted: 保存と配信外のイベント

利用者が次の2点を明示的に選択した。

1. **チャット本文は無期限保存し、必要なときに手動で削除する。**
2. **アプリの記録機能が稼働中なら、配信外のフォローなどのイベントも記録する。**

配信外の出来事はチャンネルのイベント履歴に残し、配信中の実績に混ぜない。
配信外イベントの記録は、配信外のチャット本文も収集するという意味ではない。
チャット本文の収集は初期案では配信中に限定し、保存した本文に期限を設けない。

## 5. Recommended: 記録の開始・終了と機能停止

| 状況 | 記録・表示の扱い |
|---|---|
| ブラウザを閉じた | アプリ側の記録は継続する |
| Twitchのライブ開始を確認 | Twitchの配信IDにひも付く記録を開始する |
| 配信途中でアプリが起動・復旧 | 同じ配信IDなら同じ履歴を再開し、未観測区間を明示する |
| Twitchの配信終了を確認 | 記録を確定する。終了時刻の精度と確認時刻は区別する |
| アプリとTwitch間が切断 | 終了と即断しない。接続・データ鮮度を悪化状態として表示する |
| 新しい配信IDを確認 | 前の配信とは別の履歴にする。日付やタイトルで自動結合しない |
| 日付が変わった | 同じ配信IDなら一つの配信として継続する |
| 自動投稿を無効化 | 投稿だけを止め、観測・統計・イベント記録は継続する |
| 全体のBot停止を実行 | 記録と自動実行を止め、外部公開用スナップショットを消去する |

「自動投稿の無効化」を、既存の全体停止操作の意味へ上書きしない。
外部の `GET /api/stream/status` は既存の読み取り専用・キャッシュ限定・
配信終了またはBot無効時の消去契約を維持する。詳細な鮮度・記録状態はv2画面/APIで扱う。
送信間隔、API呼び出し制限、認証、ワーカーの起動・終了も既存の保護範囲を守る。
全体停止中の自動バックアップも休止し、手動バックアップだけを利用可能にする詳細案は
[08](08-nas-backup-and-settings.md)を参照する。再開時に停止期間の記録や外部操作を後付けで再実行しない。

## 6. Recommended: 数値とデータ品質

- 同接はTwitchの視聴者数の観測値を使い、チャット接続人数から計算しない。
- 元の観測値と取得時刻を保持し、グラフの表示用に間引いても元の最大値を失わない。
- 平均同接は観測時間を考慮して集計し、欠測を0人として含めない。
- 欠測区間をまたぐ補間で、見ていない時間の同接を作らない。
- 最大同接は観測できた区間の最大値。配信全体を取り切れたか併記する。
- 指標ごとに観測範囲を管理する。同接が取得できてもイベント受信だけが
  切断中なら、全データを完全取得とは表示しない。
- 比較先が短い場合、終了後を0人で延長しない。
- 配信途中のカテゴリー変更を時刻付きで記録する。複数カテゴリーの配信を
  最後のカテゴリーだけで全時間分類しない。
- 参加回数は同一人物・同一配信IDにつき1回。再接続で重複加算しない。
- 個人の滞在はチャット接続から観測した時間として表示し、通信断を滞在扱いしない。
- プレビューの折れ線補間や集計式は本番のサンプリング契約の決定ではない。
  計測間隔と観測値の有効範囲・時間加重平均の詳細案は[10](10-viewer-metrics-and-data-quality.md)で具体化する。

## 7. Recommended: イベント、フォロー、マーカー

イベントには、種類、対象者のTwitch ID、取得できる発生時刻、受信時刻、
時刻の出所、関連する配信IDを保持する。配信が特定できない場合は未分類とし、
受信時刻だけで直近の配信へ押し込まない。

- 発生時刻と配信期間を照合できる場合は配信に関連付ける。
- 配信外と確認できたイベントはチャンネル履歴だけに残す。
- 後から取得したフォロー日時は、初めて検知した時刻と区別する。
- フォローの受信と一覧同期で同じ事実を二重加算しない。
- EventSubの再送はメッセージIDで重複排除する。
- ギフト送信と受領など、同じ出来事に関する複数通知を指標ごとのルールで集計する。
- フォロー解除は正常に完了した全件同期などの根拠から確認し、
  API失敗や途中までの一覧取得で解除と判定しない。
- 解除・再フォローを上書きせず履歴として残す。
- マーカーはTwitchが返す位置・ID・結果を保存し、ローカルメモと対応付ける。
- マーカー失敗時もメモは残す。遅れて自動再送し、異なる位置へ印を付けない。
- タイムアウトで操作結果が不明な場合は、未作成と断定せず確認待ちとする。

TwitchのWebSocket接続が失われた後、再接続・再購読までに失ったイベントは
再送されない。現在状態を再取得できても、過去のイベント列を完全復元できるとは
扱わない。欠測や再取得の出所を履歴に残す。
出典: [Handling WebSocket Events](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/)、
[EventSub Subscription Types](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/)。

## 8. Recommended: 保存・削除・バックアップの範囲

| データ | 初期の扱い |
|---|---|
| 同接の観測値・集計・配信メタデータ | 期限を設けず保存する |
| フォロー・イベント・マーカー・メモ | 期限を設けず保存する |
| チャット本文 | Acceptedのとおり無期限・手動削除 |
| 動作確認用のログ | 配信履歴と分ける。保持期間は後で決める |
| VOD本体 | 既存の独立機能と保存境界を維持。自動ダウンロードは初期無効 |
| 旧版のデータ | 移行後も元データを残す。自動削除しない |

手動削除は「期間内のチャット本文」「配信履歴」「動画ファイル」など対象を分け、
実行前に対象と件数を示す。本文だけの削除で同接・発言数・イベントまで消さない。
関連レコードを含む配信全体の削除では、その影響を別に明示する。
削除済み本文をイベント詳細や操作ログへ複製して残さない。

バックアップと稼働中データの削除は別の範囲である。復元によって削除済み本文が
戻る可能性と、バックアップ内の保持を復元・削除の仕様に含める。

バックアップは配信データ、プリセット、ルール、メモ等を対象とし、動画本体や
認証情報は混ぜない。2026-09-06に保存先はNAS、頻度は配信終了後＋1日1回と決定した。
具体的な転送・世代管理・設定画面は[08の設計](08-nas-backup-and-settings.md)を参照する。
移行・更新前のバックアップと復元検証を実装計画に含める。この作業でバックアップ処理は実行しない。
容量不足時は履歴を勝手に削除せず、保存できない状態を示す。

## 9. Recommended: 移行と開発の順序

1. 今回の合意を既存要件・UI・データ設計へ対応付ける。
2. 現在のv2コードを調べ、利用できる基盤と不足分を整理する。
3. 記録、イベント、同接、人物履歴を架空データで検証する。
4. 読み取り専用画面で履歴・数値・欠測を確認する。
5. メモ・配信セット・マーカー等の操作を機能単位で接続する。
6. 自動投稿・予想を引き継ぎ、チャットコマンドを初期無効で追加する。
7. 元データを保持する移行と復元を検証し、配信外の時間帯に切り替える。

旧版と新版が同じ永続データへ同時に書き込まない境界は維持する。
移行では配信件数、観測件数、人物ID、フォローの記録、メモ、セット・ルール、
VODの参照を照合する。過去の計算式と新しい計算式による値の違いは、元値と出所を
保持して説明可能にし、差を隠すために元データを上書きしない。

従来のモデルでは失われていた再フォロー履歴などを、移行時に推測で作らない。
移行不能・不明・不正なレコードは報告し、元ファイルを保持する。
実データの移行、デプロイ、公開はこの設計作業の実行範囲に含めない。

## 11. 設計検証の例

- 自動投稿が無効でも、配信中の観測値・チャット・イベントが保存される。
- ブラウザの切替や終了が記録に影響しない。
- 配信外のフォローはチャンネル履歴に残り、次の配信の新規フォロー数に混ざらない。
- 途中復旧は同じ配信IDを再利用し、欠測を0人・イベント0件と表示しない。
- 重複イベント、再接続した人物、一覧同期からの再発見で二重加算しない。
- 不完全なフォロワー一覧取得で大量解除が発生しない。
- 再フォローで以前のフォロー・解除確認の履歴が消えない。
- メモや配信セットの保存だけでTwitchへの操作が起きない。
- マーカーの結果不明・失敗を成功と表示せず、ローカルのメモが残る。
- 本文の手動削除が同接集計やイベントを巻き添えにしない。
- 旧版の元データを変更せず、移行後の数値・欠測・未分類を説明できる。
