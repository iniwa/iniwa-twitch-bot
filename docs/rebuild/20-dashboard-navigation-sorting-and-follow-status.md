## 3. 見た目と表示密度

### 3.1 共通ナビゲーション

- 各画面で重複するナビを共通Jinjaテンプレートへ切り出し、並び順と現在地判定を一元化する。
- デスクトップのサイドバーは幅184pxを基準にする。1項目44px高、間隔4px、左右余白12px。
- 各項目に20pxの線画SVGアイコンと日本語名称を置く。既存の紫系アクセントを使用し、外部アイコン配信や画像生成は不要。
- 選択中は薄いアクセント背景、左3px線、太字。hoverとキーボードfocusも別の状態として用意する。
- アイコンは装飾として`aria-hidden="true"`、リンクの名前は見える文字から取得する。色だけで現在地を示さない。
- ライブ詳細・人物詳細等でも所属する主項目を選択状態にする。予想画面では自動化を選択する。
- 読み取り状態から得られる場合だけライブ項目に短い「配信中」を付ける。ナビのための新規Twitch呼び出しは行わない。
- メインナビは`nav`内の実際のリンクと`aria-current="page"`を使う。ページ遷移をARIAのtab操作に置き換えない。
- コミュニティの人物／イベント／フォロワー／チャットにも選択背景・下線を付け、現在地を明示する。
- 768px未満は名称を残す折り返しナビにする。アイコンだけの省略や横にはみ出す固定サイドバーを作らない。

概略（例示データ・最終デザインではない）:

## 4. 瞬時に近い画面切替

### 4.1 採用方式

Flask + Jinja + Vanilla JavaScriptを維持し、**共通shellと段階的な部分遷移**を導入する。
初回・直接URL・JS無効時は完全なHTMLを返し、JSが使える内部遷移だけ`main`の内容を交換する。
React等の新規フレームワーク、Service Worker、外部CDNは導入しない。

初期実装では既存HTMLのGETをfetchし、`DOMParser`で共通契約の`main[data-page]`とtitleを抽出する。
別のHTML描画系統や、画面ごとに同じ表示をJSONから作り直す二重実装は持たない。
必要なページmoduleとCSSは固定の対応表から読み込む。HTML中のscriptの再実行や`eval`は行わない。
既存のグラフ用`application/json`はデータとして読み、文字列の挿入はエスケープ／`textContent`を維持する。

### 4.2 遷移の契約

1. 同一origin・許可済みv2画面への修飾キーなしの左クリックだけを捕捉する。
2. URLはFlaskの`url_for`で生成されたものを使う。`/v2/control`等の既存経路を維持し、`/`のホスト側遷移も壊さない。
3. Ctrl/Cmdクリック、別タブ、download、外部リンク、旧画面、ログイン／OAuth、未対応経路は通常遷移を維持する。
4. 読み取り一覧のGETフォームも同じ仕組みを使う。ソート・filter変更で`cursor`を消して先頭へ戻す。
5. 対象の取得済み内容があれば即時に表示してから裏で再取得する。未取得なら共通shellを残して対象名と軽いloadingを表示する。
6. 遷移成功時にURL、title、ナビ選択、h1を一致させる。通常遷移はh1へfocus、戻る／進むは保存したスクロール・focusを復元する。
7. `pushState`／`popstate`に対応し、再読み込みと共有URLでも同じ条件を再現する。hashの自動化内選択も保持する。
8. 遷移ごとに世代IDを付け、古い応答が新しい画面を上書きしない。離脱時は読み取りfetchをAbortControllerで止める。
9. fetch失敗時は表示中の内容を残して再試行を示す。未取得画面には対象ページ内エラーを出し、旧ページを新ページと偽らない。
10. 応答がログインへのredirect、想定外URL、またはshell形式不一致なら、検証した同一originの通常遷移へ戻す。自動再試行をループさせない。

ソート変更では表を毎回空にせず、旧内容に「並べ替え中」を示す。取得成功まで旧見出しの確定状態を保持する。
通信失敗時はURL・選択UIも最後の成功条件に整合させる。

### 4.3 moduleのライフサイクルと操作保護

- 各画面moduleは`mount(root, context)`で初期化し、`unmount()`相当の後始末を返す。
- DOM検索は渡されたrootを基準とし、interval、resize listener、observer、未完了の読み取りを解除する。
- 共通日時整形・ナビ処理を一度だけ登録する。画面往復で二重送信・ポーリング増殖を起こさない。
- 表示している画面の既存ポーリングだけを動かし、バックグラウンドタブでは休止する。復帰時に一度再検証する。
- 人物メモ・セット等の既存下書き保持を維持する。自動化・設定も編集途中を再取得で上書きしない。
- 下書きは対象IDと保存時revisionに結び付ける。別人物・別配信へ適用しない。既存外の下書きは原則メモリ内とする。
- Twitch操作、予想の確定、削除preview、復元操作の実行可能状態をキャッシュから復元しない。復帰後の確認が完了するまでボタンを無効化する。
- 書き込み中の操作は画面外でもIDと結果を追跡し、自動で再送しない。読取fetchの中止とサーバー操作の取消を混同しない。
- 保存済み結果を関連画面へ反映し、削除後のチャット本文が戻るような古い表示を残さない。

### 4.4 キャッシュと鮮度

| 種類 | 方針 |
|---|---|
| 読み取り画面 | チャンネル・認証セッション境界、正規化URL、query、画面仕様版をキーにメモリ保持 |
| 保存量 | 最大5画面かつシリアライズ相当2MiBまで、LRU。巨大チャット／グラフは上限超過なら再利用しない |
| 再利用期間 | 最終成功取得から60秒以内は即時表示し裏で検証。それより古ければ表示用キャッシュを破棄 |
| 画面状態 | スクロール、ソート、filter、編集中下書きをデータキャッシュと別に管理 |
| 操作画面 | shellと下書きのみ再利用可。状態と操作可否は既存APIで再検証 |
| 無効化 | 保存・削除・停止・復元候補関連の成功時に関連キャッシュを破棄。認証／チャンネル変更では全破棄 |
| 保存場所 | HTTPの`Cache-Control: no-store`を維持。新規の個人データをlocalStorage、sessionStorage、Cache APIへ複製しない。既存下書き保存は維持 |
| 先読み | 許可した履歴・コミュニティの読み取りリンクをhover／focus後に1件だけ。操作・認証画面、全履歴の一括取得は対象外 |

裏の更新で行順を勝手に変えない。内容の版が変われば「新しい記録があります／更新」で先頭から取得する。
初回取得日時・最終検証日時を保持し、通信失敗を「最新」にしない。ライブの新鮮さはサーバーsnapshotの観測時刻で判断する。
一度表示した60秒より古いページまで自動消去する必要はないが、鮮度表示と操作可否の制約は適用する。

| 未取得ページへの切替 | 対象名・loadingの初回paintまで100ms以下。ローカル接続・架空DBで内容表示p95 500msを目標 |
| 縦の情報密度 | 1440×900・100%表示・同じデータのコミュニティ一覧で、上部操作を含めた可視行数を現行比25%以上増やす |
| 往復操作 | 主要画面を20往復して不要なtimer／listener／fetchが増えず、キャッシュが上限内 |

Solは同一の架空データ・ブラウザ条件で変更前後を比較する。warm／coldそれぞれ30回以上を測り、p50・p95、
HTML転送・DB処理・mount／paintを分けて記録する。200msの通信遅延条件も追加し、warm表示が通信待ちにならないことを確認する。
初回通信、期限切れキャッシュ、認証確認、大量集計まで常に瞬時とは約束しない。
上記の配備後確認で実機の単発Navigation TimingとFCPは測定した。Chrome DevTools MCPを使う正式なLCP／INP／CLS trace、
30回以上のp50／p95、200ms遅延条件、変更前との可視行数比較は未実施であり、単発値で4.5の性能目標達成とは判定しない。

## 5. ソートと一覧の共通契約

### 5.1 対象と初期順

すべての対象で昇順・降順を切り替えられる。日時は新しい順を初回選択、名前は昇順、数値は大きい順を初回選択とする。
既定表示は下表。列見出しのbuttonと`aria-sort`を使い、狭い画面には同じ状態を操作する「並び順」selectを設ける。
表示の並べ替えによって配信セットの適用順、自動投稿の実行順、バックアップの保存・削除順を変えない。

| 一覧 | ソート対象（APIの許可キー） | 既定 | 絞り込み／補足 |
|---|---|---|---|
| 人物 | 初回記録`first_seen_at`、最終記録`last_seen_at`、発言を確認した配信数`recorded_streams`、名前`name` | 最終記録desc | `follow_status=following/not_following/unknown`、既存`stream_id`。初回記録列を追加 |
| 人物の配信参加 | 最初の発言`first_seen_at`、最後の発言`last_seen_at`、発言数`comment_count` | 最後の発言desc | 現在の人物IDを維持。実視聴時間と呼ばない |
| フォロー状況（新設） | 現在または直前のフォロー日時`followed_at`、状態確認日時`evidence_at`、名前`name` | 状態確認日時desc | 現在の状態で絞る。1人1行 |
| フォロー変更履歴 | フォロー日時`occurred_at`、検知日時`detected_at`、名前`name` | 検知日時desc | `kind=follow/refollow/unfollow_detected`、既存`user_id`。1事実1行 |
| イベント | 発生日時`occurred_at`、受信日時`received_at`、従来の表示日時`sort_at` | `sort_at` desc | `stream_id`、`attribution`を維持。発生／受信を別列にする |
| チャット | 発言日時`occurred_at` | 発言日時desc | 既存`stream_id`。会話を追う際は古い順。本文の辞書順は不要 |
| 配信履歴 | 開始日時`started_at`、平均同接`average_viewers`、最大同接`max_viewers`、記録率`coverage_ratio` | 開始日時desc | 日時は配信列の見出しから操作。新方式の表示指標で比較する |
| 配信セット | 名前`name`、更新日時`updated_at` | 名前asc | 更新日時を表示。保存済み一覧だけを並べ替える |
| 自動投稿・コマンド・予想プリセット | 名前`name`、更新日時`updated_at` | 名前asc | 種別を維持。有効／無効はfilter。進行中の予想の選択肢順は固定 |
| バックアップ保存結果 | データ保存時点`created_at`、サイズ`size_bytes` | 保存時点desc | 状態はfilter。NAS転送時刻と混同しない |

ライブの少数件の直近イベント・メモ、時間軸のグラフ、設定項目の配置にはソートを追加しない。
旧VOD管理のソート改修は本書の対象外。既存の補助導線は維持する。

### 5.2 API・ページ送り

- 既存一覧GETに`sort`、`order=asc|desc`を追加。省略時は従来の既定順を維持する。追加一覧は上表を使う。
- 既存filterを保持し、5.1のfilterだけ追加する。不明なsort・order・filter値、重複した単値パラメーターは400。
- 全件にfilter → sort → paginationの順で適用する。受信した50件だけの並べ替えを全体の順と表示しない。
- デフォルト50件／最大200件を維持。全件取得型の小規模設定一覧だけは、既存上限内の全件取得を保証した場合にJSで並べ替えてよい。
- 小規模一覧でも上限超過は明示的なエラー／ページングで扱い、黙って切った集合を「すべて」としない。
- 値の同順位は一意IDで確定する。日時・数値は生の値で比較し、丸めた表示値・JST文字列でソートしない。
- NULLは昇順・降順の両方で末尾。不明日時を0、現在日時、別の日時に置き換えない。従来のイベント`sort_at`だけは明示したfallbackを維持する。
- 名前のキーは表示名→login→IDのfallbackをNFKC・casefoldした文字列とする。同名はID順。日本語の読み仮名順とは表記しない。
- sort式・列名・orderは固定マッピングのみをSQLへ組み込み、値はbindする。利用者入力をSQL識別子として連結しない。
- 新カーソルは版、一覧種別、チャンネル、sort、order、正規化filter、NULL位置、最終値、一意ID、一覧revisionを含む。最大長は既存1024文字以内。
- カーソルは認可に用いない。各項目の型・許可値・現在の条件との一致を検証し、不整合は400。ID・NULL境界にもkeyset条件を実装する。
- 新方式で返すカーソルは条件に結び付ける。既存の2要素カーソルは従来の既定順のときだけ読み取り互換を維持し、別sortとの併用を400にする。
- 同一revisionのページ送りで重複・欠落なしを保証する。並び順に影響する更新後は新カーソルを409 `list_changed`にし、旧ページを維持して先頭更新を案内する。
- revision判定と行取得は同じ読み取りtransaction内で行う。履歴等に一覧revisionがなければ追加する。時刻だけをrevisionの代用にしない。
- 戻るはブラウザ履歴と保存済みURLで復元する。「次へ」はfilter・sortを全部引き継ぐ。ページサイズ変更もcursorを破棄する。

レスポンスは既存の`items`、`next_cursor`等を維持し、適用済み`sort`・`order`・`data_revision`を追加する。
既存カーソルには更新検出の保証を追加できないことを互換制約として記録し、新UIは新カーソルを使う。

例（新設パラメーターを含む設計上のURL）:

```text
/v2/community/followers?kind=unfollow_detected&sort=detected_at&order=desc
/api/v2/follow-history?kind=unfollow_detected&sort=detected_at&order=desc&limit=50
/v2/community?follow_status=following&sort=first_seen_at&order=asc
/v2/history?sort=average_viewers&order=desc
```

### 5.3 平均同接等の集計ソート

既存の`streams.average_viewers`等には旧方式の値が含まれるため、その列を並べ替える実装は禁止する。
ページを選んでから計算した50件だけをソートする実装も要求を満たさない。

新方式の[同接計算契約](10-viewer-metrics-and-data-quality.md)を再利用し、全対象配信の同じ計算定義・集計時点の
要約値をサーバー側で用意してからページングする。取得済み一覧の表示値とソートキーは同じ要約から返す。
再計算コストを抑えるため、配信ID・元データrevision・計算方式版・`as_of`を持つ派生要約を採用する。
平均・最大・記録率・欠測品質を保持し、チャート区間や本文は要約へ複製しない。

派生要約の保存が必要な場合は追加migrationを使い、既存migrationのchecksum・旧値を書き換えない。
既存の記録処理に接続した単一の更新担当が、観測・欠測・配信終了・インポート等による無効化を処理する。
配信中は保持時間の上限による値の変化もあるため、revisionだけでなく集計時点で再評価する。
全件更新は一括の長いwrite lockを避けて進め、完成した世代を原子的に公開する。GETからワーカーを起動しない。

初回の要約準備中は指標ソートを「集計を準備中」とし、開始日時順は利用できる。
未準備と観測なしのNULLを区別し、不完全な集合を全件の順位として返さない。
この準備を必要とする実装では、既存の停止中のローカル閲覧を維持できる読み取り計算経路も用意する。
Solはこの箇所を独立工程として検証し、完成要約と既存readerの指標が一致する証拠を残す。

## 6. フォロー解除の把握

### 6.1 取得できる事実と限界

TwitchのGet Channel Followersは現在フォローしている人とフォロー日時を返す。詳細一覧には
`moderator:read:followers`と配信者／モデレーターの権限が必要で、条件を満たさないと総数だけの場合がある。
ページ取得中にも総数は変わり得る。[Twitch API公式仕様](https://dev.twitch.tv/docs/api/reference/#get-channel-followers)

確認したEventSub種別一覧には`channel.follow`があるが、解除専用イベントは掲載されていない。
したがって本設計では現在一覧と過去の記録の差分を使い、解除操作の正確な発生時刻・理由を取得できるとは扱わない。
[EventSub公式種別一覧](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/)
公式仕様の確認日: 2026-09-07。

利用者向け常時説明は「解除は一覧同期でフォローが見つからなかったことを確認した記録です。実際の解除日時・理由は分かりません。」とする。
同期間の解除→再フォローや、記録開始前に完了した解除は完全には復元できない。
一覧からの消失が本人の操作かアカウント側の変化かを断定しない。

### 6.2 画面構成

フォロワー画面内に以下の2つの表示モードを設ける。既存の`/v2/community/followers`は変更履歴のまま維持する。

| 表示 | 内容 |
|---|---|
| フォロー状況（新経路`/v2/community/followers/current`） | 人物、最後に確認したフォロー状態、現在または直前のフォロー日時、状態確認日時。following／not_following／unknownで絞り込み |
| 変更履歴（既存経路） | すべて／フォロー／再フォロー／解除を検知。出来事、人物、フォロー日時、検知日時、取得元 |

人物画面には状態と根拠の確認時刻を表示し、同一人物の変更履歴に直接移動できるようにする。
現在フォロー中でも過去の解除履歴は消さない。「解除を検知」filterは過去の解除事実、「現在は解除確認済み」は現在状態のfilterとして区別する。
解除履歴の`occurred_at=NULL`は「—（実際の解除日時は不明）」、検知日時は`detected_at`を表示する。
フォロー状況に残す直前の`followed_at`を、解除イベントの発生日時にコピーしない。

ページ上部に「最後の成功同期」「直近の試行状態」「表示データの確認時点」を短くまとめる。
filterの件数は現在の全該当行数。変更履歴の件数を現在フォロワー数と呼ばない。
大きい数値カードや外部通知は追加せず、一覧上で把握できる形にする。

### 6.3 データ・APIの追加

- 新規`GET /api/v2/follower-status`は既存`community_people`と`follower_state`から1人1行を返す。未確認の記録人物もunknownとして扱う。
- 名前とID、`status`、`followed_at`、`evidence_at`を返し、5節のfilter・sort・cursorを適用する。
- 既存`GET /api/v2/follow-history`へ`kind`filterを追加する。現在状態で履歴を消さない。
- 状況・履歴の両方に同期情報を付ける。既存`latest_sync`は保持し、`last_successful_sync_at`とキャッシュ済み`sync_status`を追加する。
- `sync_status`は`not_started/collecting/waiting/paused/authorization_required/failed/superseded`を区別する。
  最後に成功していても現在停止中なら両方を表示する。情報を得られない場合は`unknown`を明示する。
- `last_successful_sync_at`は最後の`complete`の終了時刻。失敗・supersededの終了時刻で成功日時を更新しない。
- repositoryの最新runだけでは停止・権限不足を表せないため、既存runtimeからフォロー同期stepの結果をスナップショットとして公開する。
  runtime未接続時は永続化済み履歴を返し、現在状態を捏造しない。
- 読み取りGETと「一覧を更新」は保存済み記録／状態の読み直しだけを行う。ブラウザで開くたびにTwitch同期を走らせない。
- 既存の900秒待機・ページ処理ペースを維持する。15分は解除検知の保証時間ではなく、ページ数・429・停止・失敗で遅れることを補足する。

### 6.4 既存の解除判定を守る条件

1. 直前までfollowingとして記録されていた人物だけが解除判定の候補になる。初回同期で未知の人物を解除扱いしない。
2. 全ページの順序・cursor・重複人物・総数・終端・revisionを検証した`complete`だけを反映する。
3. 通信失敗、途中終了、権限不足、総数だけの応答、重複、cursor循環、総数変化では現在状態を維持する。
4. 同期中の新しいフォロー事実は既存どおり`superseded`にし、古い一覧で状態を戻さない。
5. 権限と応答を検証した完全な0件一覧は有効。失敗由来の空配列と区別してテストする。
6. 同じ同期の再完了で解除履歴を二重に増やさない。新しいfollow timestampの再フォローと、遅延した古いfollowを区別する。
7. 履歴・状態を同一transactionで更新する。停止・再開・再起動でも部分同期を完全な一覧として公開しない。

全件取得もTwitch全体の厳密な同時点snapshotを保証するものではない。上記の整合性検証を維持したうえで
「検知した事実」と表示する。精度を上げるための同期間隔短縮や追加の外部問い合わせは今回導入しない。
