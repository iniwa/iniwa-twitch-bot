## 2. データモデルの追加単位

既存migrationの内容・チェックサムを書き換えず、実装時点での最新版に続くmigrationを追加する。
以下は論理モデル名。SQLiteの実DDL・索引は各実装単位の検証と合わせて固定する。

| モデル | 最低限保持する意味・制約 |
|---|---|
| `collection_runs` | 収集処理の実行ID、開始・停止、異常終了判定。再起動の境界を明示 |
| `viewer_observations` | 配信ID、収集実行ID、観測ID、取得時刻、人数、取得元。新しい20秒観測を保存 |
| `observation_gaps` | 配信IDは必要に応じてnull、指標・開始・終了・理由・確定/推定。配信外の切断も記録 |
| `stream_boundaries` | Twitch開始時刻、最後のライブ確認、終了確認、終了根拠・不確実な範囲 |
| `stream_metric_summaries` | 対象区間、方式、人数×秒、集計秒数、平均・最大、カバー率、基準時刻、元データの版 |
| `stream_metadata_history` | タイトル・カテゴリー・タグの確認時刻と変化。最後のカテゴリーで過去を塗り替えない |
| `channel_events` | イベントID、TwitchメッセージID、発生/受信時刻、時刻の出所、人物ID、配信への帰属根拠 |
| `follow_history` | フォロー・解除確認・再フォローの事実を追記。検出時刻と実際のフォロー日時を区別 |
| `follower_sync_runs` | 同期の成功/失敗、全ページ完了、比較元。部分取得では解除を発生させない |
| `viewer_streams` | 人物IDと配信IDで一意。チャットでの観測範囲、発言件数。実視聴時間と呼ばない |
| `chat_messages` | 一意なメッセージID、人物・配信・時刻、本文。本文だけ削除した状態を表現可能にする |
| `stream_markers` | ローカルメモID、配信、メモ時刻、TwitchのマーカーID/位置、成功・失敗・結果不明 |
| `channel_presets` / `automation_rules` | 永続ID、版、定義、個別有効状態。並べ替えにIDを使う |
| `chat_commands` / `command_aliases` | 応答の種類・定義、権限、待ち時間。正規化名と別名はチャンネル内で重複禁止 |
| 投稿実行状態 | 定義ID・版、受信メッセージID、待機基準、期限、結果。同じ外部操作の重複受付を防ぐ |
| `prediction_presets` / `predictions` / `prediction_outcomes` | ローカルの定義とTwitch上の実体を分け、IDで状態を更新 |
| バックアップ管理 | コピーID、データ時点、作成理由、検証結果、容量、転送状態、保存世代、NAS確認情報 |

現行の `stream_samples` はチャット等の値も含む既存・移行データとして保持する。
新しい同接観測を別の `viewer_observations` に保存し、意味が違う1分行を20秒行へ無断で分割しない。
旧平均・最大と新計算の結果は出所・方式で分ける。旧レコードの不足情報を既定の0で埋めない。
人物メモは既存の人物IDに結び付ける。表示名の変更や別名で人物を分割しない。

## 3. 記録と変更の一貫性

- 同接の観測とその版、イベントの重複排除と保存は、途中状態を公開しないトランザクション境界を持つ。
- 成功した保存後の版を読み取りモデルへ公開する。保存失敗時は古い値を「保存済みの最新値」に見せない。
- HTTPリクエストで収集ワーカーを起動・増殖させない。公開ステータスAPIは引き続きローカルのコピーだけを読む。
- イベント・フォローの配信帰属は発生時刻と根拠で判断し、受信時刻だけで次の配信へ押し込まない。
- チャット本文の削除では件数・同接・イベントを残す。管理ログやJSONの複製から本文が残存しないよう検証する。
- 削除の事前確認は対象・期間・件数と版を返す。確認後に対象が変わったら再確認を求め、未確認分を含めない。
- メモ・セット・ルールは版の競合を検知し、別画面の編集を黙って上書きしない。
- 外部操作は受付と結果を区別し、タイムアウトは結果不明。再起動・再送・復元で勝手に再実行しない。
- ローカルメモを先に保存してからTwitchマーカーを要求する。Twitch失敗でメモを失わず、遅延再送しない。
- Twitch APIが任意の冪等キーに対応していると仮定しない。アプリ内の重複排除と外部結果の照合を両方設ける。

## 4. v2 APIの追加契約

以下は将来の経路案であり、現行ルートとして案内しない。既存の `/api/v2/live` は互換性を確認しながら拡張する。
全GETはローカル記録・公開済みスナップショットを読む。同期・マーカー・予想等の外部操作は明示したPOSTへ分ける。

| 経路案 | 用途と結果 |
|---|---|
| `GET /api/v2/streams` | 日付・カテゴリー・出所で配信一覧。各集計に方式と記録品質を付ける |
| `GET /api/v2/streams/<id>/analytics` | 同接、区間集計、欠測、イベント参照。同じ記録版で返す |
| `GET /api/v2/stream-comparisons` | 2配信を経過時間で比較。全体/共通の時間範囲と方式差を明示 |
| `GET /api/v2/viewers/<id>/history` | 人物の配信参加・フォロー履歴。表示名ではなくIDを使用 |
| `POST /api/v2/streams/<id>/markers` | ローカルメモとTwitchマーカーの受付。両者の保存・実行状態を返す |
| `POST /api/v2/chat-body-deletion-previews` | 期間内の本文削除候補と影響、確認用の対象版を返す |
| `POST /api/v2/chat-body-deletions` | 確認済み対象の本文だけを削除する |
| `POST /api/v2/commands` / `PATCH /api/v2/commands/<id>` | コマンドの作成・編集。定義保存では投稿しない |
| `POST /api/v2/automation-previews` | 架空の入力・状態で条件と応答を評価。外部通信をしない |
| `POST /api/v2/predictions/<id>/lock` | 受付終了を要求。Twitchの結果を確認して状態を更新 |
| `POST /api/v2/backups` | 1回のコピー作成・転送を予約し、処理IDを返す |
| `POST /api/v2/restore-previews` / `POST /api/v2/restores` | 候補の検証と、確認済み候補からの排他的な復元 |

既存のセット・ルール・予想確定等のCRUD案は[04](04-data-and-api.md)に従う。
バックアップ状態・操作履歴・コマンド一覧の読み取りもローカルのページング付きqueryとして実装単位内に含める。

一覧は初期50件、上限200件のカーソル方式。集計の時刻はUTC、画面でJSTへ変換する。
グラフは対象範囲と点数予算を要求し、応答に間引き方法・表示可能範囲を明示する。
欠測区間とイベント一覧は別々にページング可能にし、取得したページだけで全体件数や完全取得を判断しない。
数値の欠落は `null`、値の出所と理由は別フィールド。欠測や空リストをエラーに紛らわせない。
配信ID・日時・期間・件数を入力検証し、旧analyticsのID検証を弱めない。

集計には少なくとも `method`、`data_revision`、`as_of`、`range_start`、`range_end`、
`weighted_viewer_seconds`、`covered_seconds`、`coverage_ratio`、`average_viewers`、`max_viewers`、
指標ごとの品質・終了時刻の確かさを返す。内部の認証情報や運用パスは返さない。

## 5. 実装順序と完了条件

工程はソース上の設計・実装・隔離検証までを進める単位であり、工程完了を本番への切替許可とは扱わない。
前提が未確定の外部接続はfake/null境界で開発を進め、認証情報や本番DBを探して補完しない。

| 順序 | 成果物 | 終了条件 |
|---|---|---|
| A. 同接と欠測 | 純粋な集計処理、観測・区間モデル、前進migration、架空データ | 10の数値例・境界例が合い、既存migrationを変えず、新旧の方式を分けられる |
| B. 履歴の読み取り | 履歴一覧・詳細・比較、記録品質とグラフ | 数値と表示が同じ版を使い、欠測をつながず、画面アクセスがTwitchを呼ばない |
| C. イベントと人物 | チャット・イベント・フォロー履歴・人物参加、記録側のfake入力 | 二重受信・部分同期・配信外・再フォロー・本文削除の整合性が保たれる |
| D. 配信中の操作 | 新ライブ画面、メモ、セット、マーカー、操作結果 | 保存と適用が分かれ、部分失敗・結果不明でも情報を失わない |
| E. 復旧の基盤 | ローカルバックアップ、NAS転送境界、復元、インポーター拡張 | 候補DBで往復検証、失敗時の保全、秘密・動画の除外。実NAS未接続なら明示 |
| F. 自動化 | 09のルール・コマンド・予想と共通送信制御 | 初期無効、待ち時間、停止、結果不明・再起動で意図しない投稿がない |
| G. 外部接続の統合 | 認証主体・Twitch adapter・収集ワーカー・既存機能の接続 | fake契約が通り、単一writer・停止・pacing・公開ステータスの保護が通る |
| H. 移行と切替準備 | 比較レポート、復旧手順、旧版へ戻す範囲 | 実行対象と戻し方を具体化し、既存配備境界を維持。実環境検証を別記 |

外部アダプターの契約はA〜Fでも先に定義する。Gまで記録形式と認証の設計を先延ばしにする意味ではない。
一つの収集結果を複数画面が読む。旧版と新版を比較する間も、同じDBへ二つの記録処理を書かせない。
必要なレビューは安定した差分に対して行い、変更後は影響する検証をやり直す。

## 6. 残す未決定事項

### 実装の初期値として進められるもの

- 20秒取得・30秒の計算上の持ち越し・60秒で現在値を「—」にする設計。
- 自動投稿15分・2コメント、コマンド30秒/同じ人60秒、予想受付2分という変更可能な初期値。
- 08のバックアップ休止・容量制限。容量は実サイズを確認して初期設定時に調整する。

これらはRecommendedのまま検証対象にする。一般的な「進めてよい」を各数値の明示的な選択へ書き換えない。

### 接続・移行前に必要な事実

- 配信者とBotの実際のアカウント構成、利用する機能に必要な認可。
- NASの専用保存先、転送担当・方式、書き込み権限、マウント切断の検出と結果照合。
- 実データの対象・量・旧形式の差、実行環境の空き、停止可能な切替時間。

これらが不明でもA〜Fの設計と隔離したソース実装は進められる。
本番移行・デプロイ・公開・NASへの実接続は、その具体的な作業範囲で扱う。
