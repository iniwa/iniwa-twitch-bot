# 10. 同接・集計・記録品質の契約

更新日: 2026-09-06

## 1. 設計の位置づけ

[07](07-recording-and-workflows.md)で合意した平均同接・最大同接・推移と、
配信中のイベントを確認する目的を具体化する。以下の数値・計算方法は実装に進めるためのRecommended。
現行実装、Twitch自身の分析値、実データで測定済みの結果とは区別する。

## 2. 現行との差と取得方針

[現行ワーカー](../../services/workers.py)には20秒の確認間隔と60秒のログ保存間隔がある。
履歴の平均は保存時の値の合計と件数から計算し、最大値も保存時の値から更新している。
[履歴の読み取り](../../routes/analytics.py)もログの値の平均・最大を扱う。
新版では、取得できた同接の元の観測値を残し、表示用の間引きや1分集約でピークを失わないようにする。

| 項目 | 新版の初期契約 |
|---|---|
| 同接取得 | バックグラウンドで20秒間隔を目標。重複する取得処理を起動しない |
| 観測値の保存 | 有効な取得結果を1件ずつ保存。1分の平均だけには置き換えない |
| 1分集約 | チャット件数などの集約・高速表示用。元の同接と集計根拠を残す |
| 正常時の値の持ち越し | 次の観測まで、最長30秒。同じ収集実行区間内だけ |
| 更新の遅れ | 観測から30秒を超えたら「更新遅延」。最後の観測時刻を併記 |
| 現在同接の表示 | 60秒以上更新がなければ主表示は「—」。最後の値は別に残す |
| 画面の取得 | アプリのスナップショットを読む。画面数や再読み込みでTwitch取得を増やさない |

20秒はアプリが取得を試みる目標であり、Twitchの内部更新頻度や秒単位の実視聴者変化を保証しない。
API制限・失敗時は共通の制御で待機し、その分を過去の観測値で埋めない。
正常な `viewer_count=0` は有効な0人。欠落、負値、不正な応答、通信失敗は0人に変換しない。

同接は対象チャンネルのGet Streamsの `viewer_count` を用いる。
チャット接続者の一覧や人数は別の情報で、視聴者リストから同接を計算しない。
出典: [Get Streams](https://dev.twitch.tv/docs/api/reference/#get-streams)、
[Get Chatters](https://dev.twitch.tv/docs/api/reference/#get-chatters)。

## 3. 平均と最大

計算方式名を `bounded_hold_v1` とし、元の値と計算方式を保存する。
20秒ごとの瞬間値から期間の値を推定するため、正常な観測の間では直前の値を短時間持ち越す。
これは計算上の仮定であり、その間ずっと同じ人数だったと観測した意味ではない。

観測を時刻順に並べ、時刻を `t_i`、人数を `v_i` とする。
各観測が計算に使える区間は、次のうち最も早い時刻で終わる。

1. 次の有効な観測の時刻。
2. `t_i + 30秒`。
3. その観測後に記録した取得失敗・収集停止などの境界。
4. 分析対象の終了時刻、またはライブ表示の集計基準時刻。

開始時刻は `t_i`。集計範囲と重なる部分だけを使い、その秒数を `w_i` とする。
収集の再起動や明示した欠測区間をまたいで値を持ち越さない。
停止時刻が残っていない異常終了でも、最後の値を30秒より先へ伸ばさない。

```text
観測を根拠に集計できる秒数 C = Σ w_i
人数 × 秒の合計 A = Σ (v_i × w_i)
平均同接 = A / C                 （C > 0 の場合）
記録カバー率 = C / 対象期間の秒数
```

- `C=0` の平均は `null`、画面では「算出できません」。0人とはしない。
- 対象期間が0秒または不明なら、カバー率も `null`。同じ理由で100%と表示しない。
- 最大同接は対象範囲の有効な元の観測値の最大。期間を持たない最後の観測点も対象にできる。
  観測がなければ `null`。最大値を記録した時刻も保持する。
- 平均は表示時だけ小数1桁に丸める。途中の分平均を単純平均せず、AとCを足し合わせて再計算する。
- 集計範囲は通常 `[開始, 終了)`。ライブ時の最大値には集計基準時刻ちょうどの最新観測も含める。
- 配信開始から最初の観測までを最初の値で逆向きに埋めない。
- ライブ集計の最後の区間は暫定。終了境界・遅れて到着した有効な情報で再計算できるよう版を付ける。
- 日付をまたいでも配信IDが同じなら1配信。日次分析だけで必要に応じて区間を切り分ける。

### 検算用の架空例

| 例 | 観測（開始からの秒: 人数） | 終了 | 集計秒数C | 人数×秒A | 平均 | 最大 |
|---|---|---|---|---|---|---|
| 通常 | 0:10、20:20、40:30 | 60秒 | 60 | 1200 | 20.0 | 30 |
| 間隔が不均等 | 0:10、10:30、40:20 | 60秒 | 60 | 1400 | 23.3 | 30 |
| 長い欠測 | 0:10、20:20、120:30 | 140秒 | 70 | 1400 | 20.0 | 30 |
| 同上、40秒で失敗を検知 | 0:10、20:20、120:30 | 140秒 | 60 | 1200 | 20.0 | 30 |
| 正常な0人 | 0:0、20:0 | 40秒 | 40 | 0 | 0.0 | 0 |
| 観測なし | なし | 60秒 | 0 | 0 | 算出不可 | 算出不可 |

長い欠測の例では50〜120秒の70秒間を集計しない。記録カバー率は50%。
40秒で失敗が分かっていれば40〜120秒を欠測とし、カバー率は約42.9%。
「欠測を0人で平均に含める」「20人を120秒まで持ち越す」のどちらも行わない。

## 4. 配信の終了と期間の確かさ

開始にはTwitchが返す配信IDと開始時刻を使う。アプリの起動時刻を配信開始に置き換えない。
通信失敗だけでは配信終了としない。新しい配信IDは別配信とし、タイトルで結合しない。

- `last_live_observed_at` と `offline_confirmed_at` を分ける。
- 正確な終了時刻が得られない場合は、最後のライブ確認からオフライン確認までを終了の不確実な範囲とする。
  UI上の長さは「終了確認までの時間（概算）」とし、集計範囲の終端にはオフライン確認時刻を使う。
- 後日、裏付けのある終了時刻が得られたら出所と改訂を記録して再計算する。VOD時間との単純一致を仮定しない。
- 再開時に既に配信が終わっており終了時刻を特定できない場合、配信時間・カバー率を無理に確定しない。
  分析可能な観測範囲と集計秒数を表示し、カバー率は `null` とする。
- Bot停止は配信の終了ではない。停止以降は欠測として扱い、公開スナップショットは従来どおり消去する。

## 5. 記録品質とグラフ

同接、チャット、EventSub、チャット接続者、フォロワー一覧同期の記録品質は別々に管理する。
同接が正常だからイベントもすべて保存できた、とまとめて表示しない。

| 状態 | 表示例 |
|---|---|
| 通常の収集 | 平均20.0人 · 同接カバー率99.4% |
| 途中から収集 | 平均20.0人 · 配信開始から12分は記録なし |
| イベントだけ切断 | 同接は更新中 · イベントは21:10〜21:14に未記録の可能性 |
| 終了時刻不明 | 平均20.0人 · 集計できた時間1時間20分 · 配信全体のカバー率不明 |
| メタデータのみ | 配信情報のみ · 同接の観測なし |
| 旧版の集計のみ | 旧方式の平均18.2人 · 新方式の再計算に必要な観測なし |

「カバー率100%」はこの計算契約の時間範囲を満たした意味で、秒ごとの実人数や全イベントの完全取得保証ではない。
機能を意図して無効にしていた期間も欠測理由に残し、トラブルによる欠測とは説明を分ける。

- グラフは有効区間を段差で描き、欠測で線を切る。欠測部分を滑らかな線でつながない。
- 長い配信では時間の区画ごとに先頭・末尾・最小・最大を残して表示量を減らす。
  欠測境界をまたいで一つの区画に結合しない。平均・最大は間引く前のデータから計算する。
- 表示量の上限で全区間を描けない場合は「範囲を拡大して確認」と示す。
  多数の短い欠測を一本の連続線へ変換して収めない。
- フォロー・レイド・サブスク等、メモ、マーカーを同じ時間軸で選択できる。
  記録時刻しか分からないイベントはその出所を示し、正確な発生時刻と混ぜない。
- チャット件数とイベント件数は受信・保存できた分。未記録期間を0件として保証しない。

Twitchの分析値とは、取得する時点、取得間隔、対象期間、欠測、計算方式が異なり得る。
アプリには「このツールで観測・集計した値」と表示し、Twitch公式の平均や最大を再現したとは扱わない。
差を合わせるために観測値を書き換えたり、不明な補正を加えたりしない。

## 6. 配信比較

- 初期候補は同じ代表カテゴリーの直前の配信。代表カテゴリーは最も長く確認できたカテゴリーとし、
  未分類時間と複数カテゴリーを明示する。不明な場合は候補を自動断定せず直前の配信を選べるようにする。
- 横軸は配信開始からの経過時間。短い配信の終了後は0人で延長しない。
- 既定の数値は各配信全体の集計。「同じ経過時間範囲で比較」は両方の短い方までの範囲を切り出して再計算する。
- 同じ経過時間の比較でも、片方の欠測をもう片方に作ったり埋めたりしない。それぞれのCとカバー率を表示する。
- 一方の平均が `null` なら差も `null`。比較元が0なら増減率は算出不可とし、人数差だけを表示する。
- 新規フォロー件数とフォロワー純増を別項目とし、総数差だけでフォローイベント数を作らない。
- 旧方式と新方式の値を比較する場合は方式差を表示し、同じ精度の値とは扱わない。

## 7. 保存・API・検証への引き継ぎ

必要な保存項目と実装順は[11](11-implementation-contract-and-delivery.md)へ対応付ける。
集計結果には方式、基準時刻、対象範囲、A、C、カバー率、欠測理由、元データの版を含める。
UIの現在値・集計結果・グラフが別々の版を混ぜないよう、同じ読み取り単位で返す。

検証は上記の架空例に加え、サンプル1件、途中開始、失敗直後の復旧、同じ配信IDでの再起動、
日付跨ぎ、カテゴリー変更、最終区間、集計区間の切り出し、重複・順序逆転・時計補正、
表示の間引き後も最大が残ること、カバー率の分母不明を対象とする。
時計が逆行した区間は負の時間として加算せず、異常を記録して収集区間を切り替える。
同じ観測の再読込は二重計上せず、競合する別の値を無断で上書きしない。
