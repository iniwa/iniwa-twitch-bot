# 14. arm64・NAS・実ブラウザでの検証

検証日: 2026-09-06

ユーザーの実機検証の指示に基づき、対象Raspberry Piで作業ツリーの新版を実行した。
稼働アプリと同じローカルイメージのPython・Flask・gunicornを使い、ソースは専用の隔離コンテナへ読み取り専用で渡した。
既存アプリの配備切替や実Twitchへの送信は行っていない。NASの確認には新しい専用領域と架空DBを使った。

## 結果

| Windowsの全体回帰 | **318件成功、2件スキップ**、13.91秒。OSが架空シンボリックリンク作成を許可しない2件 |

実機の検証ランタイムはaarch64、Python 3.12.14、SQLite 3.46.1、Flask 3.1.3、
gunicorn 22.0.0、Werkzeug 3.1.8。新しい本番イメージのビルド・配信はしていない。
pytestとその補助パッケージは検証コンテナの一時領域にオフライン導入した。

## 発見して修正した問題

### 別モニターPCの時計差で同接が消える

実画面で、Pi側に新しい観測があっても現在同接が「—」になった。
確認時のPiの時計はPCより約2〜4秒進んでおり、ブラウザの`Date.now()`で計算した観測経過時間が負になっていた。

[集約API](../../src/twitchbot/web/control.py)に`server_time`を追加し、
[ライブ画面](../../src/twitchbot/web/static/v2/control.js)はサーバー内の時刻差から鮮度を判定する。
受信後の経過時間には`performance.now()`を使う。取得失敗が続いても1秒間隔で表示値の期限を確認し、
60秒を超えた同接を残さない。`GET /api/stream/status`と読み取り専用pilotのスナップショット契約は変更していない。

[APIテスト](../../tests/test_v2_controls.py)で、時刻を追加しても元スナップショットを変更せず外部操作を呼ばないことを確認した。
ブラウザでは前後1時間の時計差と、polling失敗時の期限切れを検証した。

### 既存VODテストが実際の設定読込を呼ぶ

読み取り専用ソースで全体テストを実行すると、VODルートの既存テスト1件が設定領域の作成を試みて失敗した。
[テスト](../../tests/test_vod_routes.py)の設定取得を架空の空設定に置き換えた。
実設定・認証情報・実行時ディレクトリに依存せず、従来のルート挙動を検証する。VOD実装は変更していない。

## 保存と並行読込の実測

CPU上限1コア・メモリ上限512MiBの隔離コンテナで、同接6時間分・20秒間隔の1,080観測を用意した。
240件のチャット保存と、3スレッドによる合計120組の読込を並行実行した。
1組の読込は配信詳細、参加人物、チャットの3問い合わせ。NASへ保存して読み戻し、別候補へ復元した。

| DB保存先 | 読込1組 p95 | 最大 | 並行処理開始から復元まで |
|---|---:|---:|---:|
| tmpfs（一時領域） | 529.00ms | 619.77ms | 15.64秒 |
| ext4（実ディスク） | 487.43ms | 540.76ms | 22.83秒 |

経過時間に初期1,080観測の投入は含めない。測定値はこの架空データと実行時負荷での結果で、
単一APIのHTTP応答時間、長期運用や1年分のデータ量に対する保証ではない。
NASへ書いたDBは各569,344バイト。元DBはローカルに置き、NAS上で稼働DBを直接開いていない。

## 再実行用の道具

- [verify_v2_device.py](../../tools/verify_v2_device.py)：架空DB、並行保存・読込、ローカルバックアップ、任意の実NASへのコピーと読み戻し、停止済み復元候補を検証する。
- [v2_device_fixture.py](../../tools/v2_device_fixture.py)：実設定を読まないWSGI fixture。Twitch操作は偽物で、画面とレスポンスに架空データであることを示す。
- [verify_v2_browser.cjs](../../tools/verify_v2_browser.cjs)：PlaywrightとEdgeで操作と表示を検証する。明示したloopback URLに限り、架空サーバーであることを確認してから変更操作に進む。

保存検証の実行例。パスは、その検証のために用意した既存の絶対パスへ置き換える。
NASの実際のマウント元を事前に確認し、`--expected-nas-source`で完全一致を要求する。
ホスト固有の接続先や秘密情報はこの資料へ記録しない。

```sh
PYTHONPATH=src python tools/verify_v2_device.py \
  --work-root /path/to/local-qa \
  --nas-root /path/to/nas-qa \
  --expected-nas-source '<verified-mount-source>'
```

NAS指定を両方省略するとローカル保存・復元のみ実行する。各実行は新しい子ディレクトリを作り、
結果の`artifact_directory`と`report.json`に識別子・集計を残す。既存DBの指定・上書き・世代削除はしない。
この初回検証時点のNASコピーは検証用だった。現在のスクリプトはアプリの転送アダプターを使う。
アダプターと自動バックアップを接続した後続の結果は[15](15-runtime-and-connections.md)を参照する。

ブラウザ検証は外向き通信を無効にしたコンテナで、gunicornをUnixソケットにbindして実行した。
SSHはPCのloopbackとそのソケットだけを接続し、Piに新しいTCP待受を公開していない。
gunicornは1 worker・4 threads。fixtureは毎回作り直し、初期チャンネルキャッシュが新鮮な間に操作検証を始める。

```sh
PYTHONPATH=src:. gunicorn --workers 1 --threads 4 \
  --bind unix:/path/to/qa/browser.sock --umask 0077 \
  'tools.v2_device_fixture:create_app()'

QA_URL=http://127.0.0.1:18502 QA_ARTIFACT_DIR=/path/to/screenshots \
  node tools/verify_v2_browser.cjs
```

上のURLは、実際に準備したSSH転送先へ合わせる。Playwrightが使えるNode環境とEdgeが必要。
ソケットと検証用領域は同じ非root UIDで扱い、本番のdata/downloadsマウントを検証コンテナへ渡さない。
実行した検証用コンテナと転送プロセスは終了させ、少量の架空バックアップ・復元候補・結果だけを専用領域へ残した。
