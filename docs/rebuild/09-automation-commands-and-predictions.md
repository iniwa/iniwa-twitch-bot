# 09. 自動投稿・チャットコマンド・予想

更新日: 2026-09-06

## 1. 状態と範囲

[07の状態区分](07-recording-and-workflows.md)に従う将来設計。
自動投稿と予想を残し、チャットコマンドを追加すること、3機能を初期無効にすることはAccepted。
利用者が操作プレビューを受け入れた画面の基本構成は、下記のAcceptedへ記録する。
それ以外の操作・初期値・制御はRecommendedであり、現在の実装や承認済みの詳細仕様とは区別する。
この資料の作成では実際のチャット投稿、予想操作、設定変更、デプロイを行わない。

| 機能 | 残す・追加する範囲 | 利点 | 制約・トレードオフ |
|---|---|---|---|
| 自動投稿 | カテゴリー・時間・コメント数で定型文を送る | 告知を繰り返す手間が減る | 条件を満たさない静かな配信では送信されない |
| コマンド | 視聴者の指定コマンドに定型文・限定した配信情報で応答 | 同じ質問への案内を用意できる | 待ち時間中の連続要求には応答しない |
| 予想 | プリセット、手動開始、受付終了、結果確定、取り消し | 内容を準備して配信中の入力を減らせる | 正解の判断と確定操作は配信者が行う |

### Accepted: 自動化画面の基本構成

- 自動投稿・チャットコマンド・予想プリセットを3つのタブで切り替える。
- 自動投稿は編集と条件テストを並べ、保存済み本文、待機時間、必要コメント数、待機理由を確認する。
- コマンドは編集と応答テストを並べ、利用者の役割・入力・待ち時間による応答の違いを確認する。
- 予想はプリセット編集と今回の予想を分け、保存だけでは開催中の内容を変更しない。
- 開始・受付終了・正解選択と確定・取り消しを区別し、対象を確認して操作する。
- 新規開始をオフにした場合や配信終了後も、進行中・未確定の予想を残す。
- 操作結果が不明な場合は、再送と状態の再確認を区別して表示する。

受け入れたのは架空データによる画面案。サンプルの件数・名前・本文、テスト内の待ち時間リセット、
成功を返す再確認操作を実際のTwitch連携の仕様としない。各種数値、一覧管理、データ/APIの詳細は引き続きRecommended。

## 2. 確認した現行ソースと引き継ぎ

- [ルールの操作](../../routes/rules.py)は名前、ゲーム、本文、間隔、最低コメント数を保存する。
  新規の既定値は15分・2コメント。
- [現在の自動投稿](../../services/workers.py)は全カテゴリー、カテゴリー指定、
  専用ルールがないカテゴリー向けのDefaultを区別し、間隔とコメント数の両方を評価する。
  配列の位置を実行状態のキーにしているため、新版では永続IDへの対応付けが必要。
- [予想の操作](../../routes/predictions.py)と[接続処理](../../services/predictions.py)には、
  プリセットの作成・編集・削除、開始、確定、取り消しがある。
  新版では「受付を締め切る」操作と、失敗・結果不明からの状態確認を具体化する。
- チャットコマンドは今回の追加要件として扱う。既存のチャット受信・統計記録を置き換えるものではない。

旧版から持ち込むルール・予想プリセットは元データを保存し、形式と現行のTwitch制約を検証する。
不適合な値を無断で丸めて有効化しない。初期無効のまま、修正が必要な項目を示す。
既存の配信ステータス、ワーカーの開始・停止、Twitchの認証・送信間隔、独立したVOD機能を保護する。

## 3. Recommended: 画面と有効化

自動化画面に「自動投稿」「チャットコマンド」「予想プリセット」の3タブを置く。
配信セットは[07で合意した独立画面](07-recording-and-workflows.md)に置く。

- 初回は機能がオフであることと「設定だけ先に作れる」ことを表示する。
- 一覧は名前、対象・呼び出し方、個別の有効状態、待機理由、最後の結果を並べる。
- 保存・複製・並べ替えはTwitchへの送信や予想開始を行わない。新規・複製は個別にも無効で作る。
- 編集画面に送信しないプレビューを用意する。初期版のテスト操作はこのプレビューとし、
  実チャットへ送るテストボタンを通常の保存ボタンに混ぜない。
- 設定画面と自動化画面に出す機能スイッチは同じ設定を参照し、二重のマスタースイッチを作らない。
- ライブ画面には有効な機能の状態と、進行中・未確定の予想を表示する。
  日常の視聴者一覧・同接・イベントより大きな領域を常時占めない。

機能をオフにしても定義や履歴を消さず、記録機能は継続する。
全体停止では自動投稿・コマンド応答とTwitch操作を停止し、公開スナップショットを消去する。
停止直前にすでにTwitchへ渡った操作は取り消せたと扱わず、結果確認待ちとして残す。

## 4. Recommended: 自動投稿

### 定義と初期値

| 項目 | 設計案 |
|---|---|
| 名前・本文 | 管理用の名前と送信する定型文を分ける |
| 対象 | 全カテゴリー／指定カテゴリー／専用ルールがないカテゴリー |
| 投稿間隔 | 初期15分。分単位で変更可能、最小1分 |
| 必要コメント数 | 初期2件。0ならコメント数による条件を使わないことを明示 |
| 有効状態 | 機能全体とルール個別の両方が有効なときに評価 |

「専用ルールがない」は、現在カテゴリーに対応する有効・入力検証済みの専用ルールがない場合とする。
その専用ルールが間隔・コメント待ちでもDefaultには切り替えない。無効な専用ルールだけならDefaultを使う。
現行の名前照合はカテゴリーIDへ移し、移行時にIDを特定できないものを全カテゴリー扱いにしない。

### 実行条件

配信中と確認でき、接続・認可が有効で、対象カテゴリー・間隔・必要コメント数の条件を
すべて満たした場合だけ送信候補にする。「15分ごとに必ず送信」とは表示しない。

- 配信開始、ルールの有効化、対象カテゴリーへの切替時を新しい待機の基準にする。
  最初の投稿にも指定間隔と、それ以降に観測したコメント数を要求する。
- 全カテゴリーのルールはカテゴリー変更だけでは待機をリセットしない。
- 成功した投稿後は、そのルールの時間とコメント数の基準を更新する。
  複数ルールが同じコメントを条件に使うことは許すが、送信はまとめて行わない。
- コメント数は対象チャンネルで新しく受信したメッセージを重複排除して数える。
  自分のBot、明示した除外アカウント、登録コマンドの呼び出しを除く。
  未識別の外部Botを完全に除外できるとは表示しない。統計用の発言数とは別のカウンターにする。
- ルールの並べ替えや名前の変更だけでは送信履歴・待機をリセットしない。
  本文・対象・条件の保存ではそのルールだけ新しい待機を開始し、旧版の送信候補を破棄する。
- 同時に複数が候補になったら、最も長く待っているものから選ぶ。同時刻なら表示順を使う。
  自動投稿同士は最低60秒空ける暫定案とし、一覧上位だけが送り続けることを避ける。
- 切断・配信状態不明では送信を止める。再接続・再起動後は条件を再評価し、
  未送信分をまとめて送らない。受信の欠測後はコメント数と間隔を新しく待機する。

表示例は「あと5分」「あと1コメント」「対象カテゴリー待ち」「接続待ち」「機能オフ」。
次回の評価予定と、条件を満たすまで未定の送信時刻を区別する。

## 5. Recommended: チャットコマンド

### 初期実装に含めるもの

| 種類 | 例 | 応答内容 |
|---|---|---|
| 定型文 | `!sns`、`!discord` | 自分で保存した案内文やリンク |
| 配信情報 | `!game`、`!uptime` | 確認済みの現在カテゴリー・今回の配信経過時間 |
| 一覧 | `!commands` | 呼び出した人が使える、有効なコマンドの案内 |

名前は例であり、勝手に実リンクを埋めたり有効化したりしない。
配信情報は既存のキャッシュから読み、コマンドごとのTwitch問い合わせを増やさない。
現在状態が古い・不明なら、その旨を返すか応答を見送り、最後の配信を現在の配信として案内しない。
人物メモ、視聴者の観測履歴、認証情報はチャット応答へ含めない。

- コマンド名、別名、応答、利用可能な人、待ち時間、個別の有効状態を保存する。
- 初期の名前は `!` と半角英数字・アンダースコア1〜32文字。英字は大文字小文字を同一視する。
  前後の空白を除いた本文全体との一致で呼び出す。文中一致・引数・正規表現は初期範囲外。
- 別名と組み込み例を含めて名前の重複を禁止する。別名は同じコマンドIDを使い、待ち時間を共有する。
- 利用可能な人は「全員」「サブスク登録者以上」「モデレーター以上」「配信者のみ」。
  「以上」にはモデレーター・配信者を含む。VIPやフォロワーを自動でサブスク扱いにしない。
  権限は受信イベントの信頼できるID・役割から判定し、不明なら権限限定の応答を行わない。
- 初期の待ち時間は同じコマンド全体で30秒、同じ人で60秒。各コマンドで変更できる。
  配信者・モデレーターも送信頻度の制限を受け、別名で回避できない。
- 初期は配信中のみ応答する。配信外イベントの記録設定とは独立する。
- 未登録・無効・権限不足・待ち時間中の呼び出しには、チャットへエラーを連投しない。
  管理画面で見送り理由と件数を確認できるようにする。
- 自分のBotや除外アカウントの発言、同じメッセージの再送には応答せず、応答の連鎖を防ぐ。

任意スクリプト、外部URLの取得、AI生成応答、チャットからの予想確定・配信設定変更は初期範囲外。
定型文と限定した配信情報から始めることで、応答内容と実行範囲を画面上で確認できる。

## 6. Recommended: 投稿経路と結果

自動投稿とコマンド応答は共通の送信制御を通す。
通常のBot投稿を最低2秒間隔にする暫定案に加え、Twitch側の実際の制限も守る。
これはアプリ側の初期値であり、TwitchのAPI上限を2秒と定義するものではない。
APIとチャット側には別の制限があるため、現在の制限情報と認証主体を共通制御で扱う。
出典: [Twitch Chat rate limits](https://dev.twitch.tv/docs/chat/#rate-limits)。

- コマンド応答を定期投稿より優先する。応答候補は最大20件、受信から15秒で期限切れとする暫定案。
  混雑や制限解除後に古い質問へ大量に返答しない。満杯なら新しい候補を見送る。
- 受付時にコマンドID・利用者IDの待ち時間を原子的に予約する。同時要求で複数候補を作らない。
  見送り・失敗でもその受付に対する待ち時間は維持し、連投による再試行を防ぐ。
- 送信直前にも機能・定義の版・配信ID・接続状態・権限・期限を確認する。
  無効化、定義変更、配信終了、全体停止、復元で不要になった候補は破棄する。
- 送信結果は「送信済み」「見送り」「失敗」「結果不明」を区別する。
  Send Chat Message APIではHTTP成功だけでなく `is_sent` と `drop_reason` を確認する。
  出典: [Send Chat Message](https://dev.twitch.tv/docs/api/reference/#send-chat-message)。
- 結果不明のチャットは自動再送しない。該当する定期投稿ルールは確認待ちにし、
  コマンドは元メッセージの再送で再実行しない。新しい呼び出しは待ち時間に従う。
- 確実な拒否や権限不足も連続再試行しない。認可不備は送信を休止し、頻度制限は解除時刻と期限を評価する。
- ログは定義ID・版・元メッセージID・時刻・結果・分類した理由を残す。
  チャット本文や利用者の入力を別ログへ複製し、本文削除後も残す構成にしない。

## 7. Recommended: 予想

プリセットの保存と開催を分け、タイトル、選択肢、受付時間を確認して手動で開始する。
初期の受付時間は2分。初期表示は2択とし、必要に応じて選択肢を追加できる。
自動開催・自動の正解判定・チャットコマンドからの確定は行わない。

2026-09-06に確認したTwitch仕様は、選択肢2〜10件、タイトル45文字以内、各選択肢25文字以内、
受付30〜1800秒、同時に進行できる予想1件。配信者の認可と `channel:manage:predictions` が必要。
利用資格はAffiliate/Partnerであり、視聴者数だけで可否を判定しない。
出典: [Create Prediction](https://dev.twitch.tv/docs/api/reference/#create-prediction)、
[Running a Prediction](https://dev.twitch.tv/docs/api/predictions)。実装時にも制約を再確認する。

| Twitchの状態 | 画面で行えること |
|---|---|
| 未開催と確認済み | プリセットから内容を確認し、新規開始 |
| 受付中（ACTIVE） | 残り時間と参加状況を確認、受付を締め切る、取り消し |
| 受付終了（LOCKED） | 正解を選んで確定、取り消し |
| 確定済み／取り消し済み | 結果を履歴で確認 |
| 状態不明・接続不良 | 最終確認時点を表示し、競合する操作を抑止して再確認 |

Twitch APIは受付中からの直接確定も許すが、アプリの推奨操作は「受付終了→正解選択→確認して確定」。
確定の確認にはタイトルと正解の選択肢名を表示し、取り消しには返還される旨を表示する。
受付終了後24時間以内に解決されなければTwitch側で取り消し・返還になるため、未確定状態を残す。
出典: [End Prediction](https://dev.twitch.tv/docs/api/reference/#end-prediction)。

- Twitchの現在状態を正とし、他画面・Twitch側で行われた受付終了や確定も反映する。
  取得失敗を「未開催」に変換しない。カウントダウンが0でも確認前にLOCKEDと確定しない。
- 作成・確定の連打は同じ操作として扱う。結果不明なら自動再送せずTwitchの状態を照合する。
  タイトル一致だけで自分の作成成功と決めず、帰属を確認できないものは不明のまま扱う。
- 機能オフは「新しい予想の開始をオフ」と説明する。進行中の予想を勝手に取り消したり隠したりしない。
  アプリが稼働し認可が有効なら、既存の予想の確認・受付終了・確定・取り消しは引き続き手動で行える。
- 配信終了後も未確定の予想を表示し、手動で整理できる。新規開始はこのアプリの初期設計では配信中に限る。
- 全体停止時はTwitch操作・自動取得を止める。最後に確認した予想と確認時刻を残し、
  アプリを再開するかTwitch側で管理する案内を示す。Bot停止はTwitch上の予想取消を意味しない。
- 開始・受付終了・確定・取消の履歴を配信のアクティビティへ関連付ける。
  配信外に確定しても開始した配信との関連を維持し、発生時刻を配信中へ書き換えない。

## 8. 実装前の対応と検証

[04のデータ設計](04-data-and-api.md)へコマンド定義・別名・利用条件・待ち時間、
定期投稿の待機基準、投稿候補の期限・重複排除、予想の結果不明状態を対応付ける。
ルールの定義と実行中の状態を分け、画面の並べ替えやバックアップ復元で外部操作を再実行しない。
[02のUI設計](02-information-architecture-and-ui.md)とAPIの受付終了操作も実装前に整合させる。

未決定事項は、今回の推奨する待ち時間・コメント条件・コマンド範囲の採否、
認証主体と権限の実構成、Shared Chatの受信元・送信先の扱い、再起動後の重複排除期間と状態移行。
Shared Chat由来の他チャンネルの発言を、このチャンネルへのコマンド・コメント条件として無条件に扱わない。

必要な検証は架空データと偽Twitch応答で行う。

- 3機能が初期無効で、設定保存・プレビューだけでは送信しない。
- 15分経過と2コメントの両方、0コメント設定、Defaultと無効な専用ルールの関係を検証する。
- 並べ替えでは状態を維持し、対象・本文変更は該当ルールだけ待機を作り直す。
- コマンド名・別名の衝突、役割不明、待ち時間、連打・再送、Bot自身の投稿を検証する。
- 送信待ち中の無効化・編集・配信終了で、古い応答や定期投稿が送られない。
- API成功かつ未送信、タイムアウト、429、認可不足を成功や即時再送に変換しない。
- 進行中の予想がある状態で新規開始を防ぎ、他の画面での確定を反映する。
- 機能オフ・配信終了後にも未確定の予想を表示し、全体停止時には外部操作を行わない。
- 復元や再起動で過去のチャット・予想操作を再実行せず、記録・公開ステータスの保護契約を維持する。
