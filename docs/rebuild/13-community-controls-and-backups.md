# 13. コミュニティ・配信中の操作・復旧基盤の初期実装

更新日: 2026-09-06

細かな工程ごとに確認待ちで止めず、[11](11-implementation-contract-and-delivery.md)のC、D、Eの基盤を続けて実装した。
この資料は初期実装時のソースと隔離検証の到達点を示す。この時点では現行アプリへの切替、実Twitch操作、実NAS接続は行っていない。
後続のarm64・実NAS・ブラウザ検証と修正結果は[14](14-device-verification.md)を参照する。

## コミュニティの記録と読み取り

[正規化した入力](../../src/twitchbot/application/community.py)と[保存・query](../../src/twitchbot/adapters/persistence/community.py)を追加した。
migration 4はイベント、フォロー事実と現在状態、同期の一時記録、チャット、人物の配信参加、本文削除の確認を保持する。
既存migration 1〜3と旧データの列は書き換えない。

- イベントの発生時刻・受信時刻、配信中・配信外・帰属不明を別に保存する。帰属は正規化入力が根拠に基づいて指定する。
  指定配信のチャンネル・開始終了区間を検証し、受信時刻だけで次の配信へ移さない。時刻不明の出来事は帰属不明に限定する。
- 同じイベントIDの再受信と同じフォロー日時の重複を抑止する。一覧同期とイベント受信から同じフォローを二重に履歴へ追加しない。
- フォロー、解除を検知した事実、再フォローを履歴として残す。解除の実時刻は不明と表示する。
- 一覧同期はページ順、カーソル循環、重複人物、総数、最後のページまで検証する。途中の取得は現在状態へ反映しない。
  同期中に新しいフォロー事実が入った場合は`superseded`とし、古い一覧から解除を判定しない。
- 配信外のチャット本文は保存しない。配信中の本文には自動の保存期限を設けない。
  同じメッセージの再受信で発言数を増やさず、人物ID・配信IDで参加記録を一意にする。
- 現段階の人物参加は発言を確認できた範囲。視聴時間・全視聴者数として表示しない。

[APIと画面](../../src/twitchbot/web/community.py)は一覧、イベント、フォロワー、人物詳細、チャットに対応する。
各一覧はカーソル方式・初期50件／最大200件で、表示したページ数と全件数を区別する。
履歴詳細から同じ配信のイベント・人物・チャットへ移動できる。

| GET | 内容 |
|---|---|
| `/api/v2/events` | `stream_id`または`attribution`で絞り込み |
| `/api/v2/follow-history` | `user_id`で絞り込み。直近の一覧同期状態も表示 |
| `/api/v2/viewers` | 記録した人物。`stream_id`で発言を確認した配信を指定 |
| `/api/v2/viewers/<id>/history` | 人物と配信ごとの発言記録 |
| `/api/v2/chat-messages` | 本文と削除済み状態。`stream_id`で絞り込み |

画面は`/v2/community`、`/events`、`/followers`、`/people/<id>`、`/chat`を使用する。
後者4つの経路は`/v2/community`を先頭に付ける。

### 本文だけの手動削除

`POST /api/v2/chat-body-deletion-previews`でUTCの開始・終了を指定し、件数と確認IDを作る。
画面ではJST入力をUTCへ変換し、終了時刻を含まない期間と件数を表示する。
`POST /api/v2/chat-body-deletions`は確認IDが指す同じ対象だけを削除する。

確認は30分で期限切れ。確認後に対象メッセージが増減した場合は409を返し、再確認を求める。
対象外の新着イベントでは確認を無効化しない。同じ削除要求の再送は結果を返し、新しい本文を追加で削除しない。
本文を消しても同接・イベント・発言数・人物参加は残す。削除済みメッセージの再受信で本文を復活させない。
イベント・操作記録に本文の複製を作らない。

これはアプリ上の論理削除であり、既存バックアップやSQLiteの過去のページを含む媒体上の完全消去ではない。
バックアップから本文が戻り得ることを削除・復元の説明に含める。

## 配信中の操作

[定義と外部操作ポート](../../src/twitchbot/application/control.py)、[保存処理](../../src/twitchbot/adapters/persistence/control.py)、
[操作サービス](../../src/twitchbot/application/live_actions.py)、[API](../../src/twitchbot/web/control.py)を追加した。
migration 5は配信セット、配信メモ、人物メモ、適用確認、外部操作の受付・結果を保持する。

- `/v2/control`は新しいライブ画面。現在同接・平均・最大、推移、確認できた人物、アクティビティ、メモを並べる。
  10秒ごとの画面更新はローカルqueryのみ。数値を更新し、リストの新着は更新ボタンで反映して操作位置を動かさない。
  配信の切替時は旧リストを消して更新を案内し、旧配信へマーカーを送らない。現在同接は古い情報を「—」にする。
- メモはローカルへ先に保存する。Twitch側で失敗・結果不明・未接続になってもメモは残す。
  外部マーカーの成功には返却IDと位置が必要。同じ操作IDを再送しても外部操作を繰り返さない。
- `/v2/presets`は保存、適用前の差分確認、適用を分ける。保存・プレビューでは外部送信しない。
  未保存の編集がある場合は適用に進めない。適用時と送信直前に定義・現在値の版を検証する。
  現在値が60秒以上古い場合は適用を見送る。空のカテゴリーIDは現在のカテゴリーを維持し、空のTwitchタグはタグを外す指定。
- Twitchへ渡すデータはタイトル・カテゴリーID・Twitchタグだけ。セットの管理名や告知用タグを送信ポートへ渡さない。
- 人物メモは記録処理と別の版で保存する。チャット受信だけでメモ編集が競合しない。
  ブラウザの同じタブ内では、人物・セット・配信メモの未保存下書きを`sessionStorage`で保持する。
- 外部操作は記録上の`dispatching`へ進めてから一度だけ呼ぶ。タイムアウトは`unknown`。
  再起動時の明示的な復旧処理は未完了操作を結果不明にし、再送しない。
  セットの結果不明が残っている間は、新しい適用を抑止して現在状態の照合を待つ。
- 実行許可ゲートは初期状態で閉じる。明示的に実行中を確認できる場合だけ外部操作へ進む。
  全体停止中もローカルメモは保存できるが、Twitchへ送らない。

| POST | 内容 |
|---|---|
| `/api/v2/presets` | 版付きのセット保存 |
| `/api/v2/preset-previews` | 現在のキャッシュと保存済みセットの差分・確認ID |
| `/api/v2/preset-applications` | 確認IDと操作IDで適用 |
| `/api/v2/streams/<id>/markers` | ローカルメモ。`marker: true`の場合だけ外部操作も要求 |
| `/api/v2/people/<id>/note` | 人物メモの版付き保存 |

読み取りには`/api/v2/control`、`/api/v2/presets`、`/api/v2/streams/<id>/notes`、
`/api/v2/people/<id>/note`、`/api/v2/control-operations/<id>`を用意した。
新しい変更APIは同一OriginのJSON要求を検証し、CORSを許可しない。
実運用への接続時には既存の管理画面・認証・公開境界を引き継ぐ。今回は独立したv2 factoryへの明示注入だけを実装した。

旧`/v2/live`の読み取り専用pilotと、公開`/api/stream/status`は変更していない。
実Twitchアダプターはまだ未接続。外部で同時に行われた編集の照合、カテゴリー検索、結果不明の解決操作は後続の統合対象。

## バックアップと復元候補

[方針・転送ポート](../../src/twitchbot/application/backups.py)、[コピー作成・候補検証](../../src/twitchbot/adapters/persistence/backups.py)、
[実行判定](../../src/twitchbot/application/backup_coordinator.py)を追加した。
コピー対象は明示したv2 SQLite DBだけで、データディレクトリ全体や動画・資格情報ファイルを探索しない。

- SQLite Online Backupで新しい専用ディレクトリへコピーし、整合性・外部キー・実際のスキーマ・migrationのチェックサムを検証する。
  未知の設定や追加スキーマを承認済みデータとして書き出さない。管理用manifestには本文・メモを複製しない。
- 既定の待機3件、領域10GiB、残す空き5GiBまたは総容量の10%を使う。事前とコピー中の容量確認、停止要求による中断を行う。
  失敗時に削除するのはその呼び出しが新規作成した不完全なファイルだけで、過去の正常コピーを消さない。
- 同一プロセス内のロックと専用領域の排他ファイルで、同じ場所への並列処理を防ぐ。
  異常終了で排他ファイルが残った場合は自動で奪取しない。実プロセス停止を確認する保守手順が必要。
- 日次はJST 04:00。配信終了の要求と同じコピーへまとめ、manifestの対象日・配信IDから再起動後も重複作成を防ぐ。
  逃した過去日分を再現せず、最新状態のコピーを1回作る。全体停止中は実行判定を休止する。
- NAS転送はホスト側のポートへ委譲する。DBと復元に必要なmetadataを渡し、同じIDでの再試行を可能にする。
  宛先の確認、サイズ・チェックサム照合済みの返答を受け取った場合だけNAS保存済みにする。
  失敗後もローカルコピーを保持し、実行判定は5分待つ。NAS未接続ならローカル保存済みと区別する。
- 保持候補は日次14日、週次4週、配信終了後3件。手動・作業前・未転送・最後の正常コピーを削除候補にしない。
  現段階は整理候補を計算する処理だけで、NASやローカルの世代を自動削除しない。
- 復元は存在しない別の候補パスだけに作成する。現在DBを上書き・切替・推測マージしない。
  候補では自動実行設定を無効化し、過去の公開用チャンネルキャッシュを消し、未完了操作・同期・削除確認を再実行できない状態にする。
  候補の整合性を再検証し、本文が戻り得ることを結果に含める。失敗した候補を稼働DBへ昇格させない。

実行判定はワーカーから呼ぶ1回分の処理であり、コンストラクター・GET・読み取り画面からスレッドやタイマーを開始しない。
実際のschedulerへの接続、配信終了IDの永続的な配送、NASの宛先確認方式、バックアップ画面、
本番の停止・作業前退避・切替・ロールバックは未実施。
